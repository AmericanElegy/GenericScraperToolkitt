# Offline interpretation backend

This is a fresh standalone implementation informed by the user's read-only FantasyBrief/Fable5 review. No code was copied and neither project is a dependency. FantasyBrief was not opened, modified, executed or deployed by this implementation.

## What works now

`src/interpretation/pipeline.js` implements a provider-neutral boundary currently restricted to an explicit **scripted** interpreter:

`supplied text → bounded passages → requested schema → scripted candidates → independent validation → human review → export`

The script returns prewritten candidates. **It does not understand arbitrary prose, call an AI service, or fetch the attributed URL.** This is the offline contract and test harness for a later interpretation adapter. Website-to-article extraction, OCR, JavaScript execution and paid inference remain disabled/unimplemented. A separate browser [Interpretation Lab](interpretation-lab.md) now accepts pasted prose with automatic quantitative suggestions and suggested columns, a manual name/number grammar, and built-in fictional fixtures. It supports manual candidate correction/addition and session-only review/export. General prose understanding is not enabled; the CLI remains a scripted contract harness. The public Worker is not deployed automatically.

## Inputs, limits, and provenance

- Supply 1–16,000 UTF-16 code units of text. Paragraph boundaries are blank lines; a single line break remains inside its passage. Reject more than 32 passages; never silently truncate.
- Supply 1–8 ordered columns: safe unique names, strict string/number types, explicit required flags, and optional finite numeric bounds. There are no fantasy-specific rules or vocabularies.
- Normalize CRLF/CR line endings to LF, retain the full snapshot, and hash both original supplied text and retained snapshot with SHA-256. Passage IDs, per-passage hashes, receipt timestamp and offsets are generated by the backend.
- Offsets refer to the retained snapshot in UTF-16 code units, **start inclusive and end exclusive**, not original webpage bytes. Leading/trailing paragraph whitespace is excluded from passages; the snapshot itself is retained.
- Source URLs are optional, user-supplied attribution, not independently verified retrieval provenance. The timestamp is receipt time, not a claim that the URL was fetched.
- Candidate responses are capped at 128 KiB, 50 records, four supporting spans per field, 2,048 code units per quotation, and 16 issue strings per record. No interpreter retries occur.

Every nonempty field needs exact supporting quotations with passage IDs. Repeated quotations require a zero-based occurrence index. The backend computes all offsets; interpreter-provided offsets are rejected. Multiple spans remain separate. Every passage needs a `records` or `no_result` outcome and reason; absent outcomes become `not_processed` and block approval. `no_result` means the **interpreter reported no candidate**, not that a validator established semantic absence.

## Validation is not meaning verification

The validator checks known columns, strict types, finite numbers, selected bounds, exact quotes, passage identities, and literal support. Supported numeric formatting is signed, ungrouped decimal notation; scientific notation and digit grouping are not inferred. A number embedded in a larger grouped number cannot qualify as a matching suffix.

These checks cannot establish entity/score association, resolve corrections or negation, or calibrate confidence. A deliberately swapped score can pass literal checks and still must remain `needs_review`. All candidates start unapproved, including apparently clean ones. Scripted source instructions are just text; the interpreter has no network, tools, or provider credentials.

Approval requires a named reviewer, a nonblank note and explicit association confirmation, with no blocking field/coverage/interpreter issues. Cross-passage associations remain flagged and can only be accepted by that explicit human decision. A candidate carrying a correction/ambiguity flag must be rejected or remain pending until a corrected candidate is validated as a **new job**. Nothing auto-approves flagged numbers.

## Raw cache and offline revalidation

Each job directory stores separate immutable-at-creation files:

- `packet.json` — source snapshot, passages, schema and packet hash.
- `response-cache.json` — raw scripted response, interpreter identity, response hash and versioned cache key.
- `validation.json` — initial validation output or invalid-response issue report.
- `reviews.jsonl` — initially empty; subsequent review events append.

Cache identity covers packet/response versions, the full packet hash and scripted interpreter/version/response identity. Validator version is deliberately separate, so cached raw responses can be checked again without an interpreter call. Every export revalidates the raw response and packet; it does not trust saved `validation.json`. Invalid response shapes are retained for diagnosis. In-memory replay caching is also supported through the module API; this is not a shared customer cache.

## Review journal and trust limits

Reviews append sequence numbers, prior-event hashes, validation/packet identity, decision, reviewer, note, confirmation, timestamp and event hash. Later events can change a row's effective status; previous events are not edited. Reordering or inconsistent changes are rejected. Revalidation that changes the validation identity requires fresh review.

The CLI uses an exclusive review lock and appends one JSON line. A partial/corrupt journal fails closed; no automatic repair overwrites history. A crashed process may leave a lock requiring investigation when no review process remains. Outputs and existing job directories are never overwritten.

This is a **local prototype**, not an authenticated audit service. Reviewer names are self-declared. Hashes detect inconsistent artifacts, but someone with write access can rewrite an entire chain and recompute hashes. Production needs authenticated authorization and protected durable storage before these decisions can serve as trusted customer approvals.

## PowerShell walkthrough

From `GenericScraperToolkitt\element-extractor`, after pulling the feature branch:

```powershell
npm.cmd run interpretation:demo
```

This writes a new timestamped directory under ignored `.interpretation`. The example is fictional: two prewritten candidates, including an intentionally flagged old score, and one no-result paragraph. Both records remain pending. It is not a live DCI extraction or automatic AI interpretation.

For a reproducible manual workflow, choose a directory name that does not already exist:

```powershell
$job = Join-Path $PWD '.interpretation\my-first-job'
npm.cmd run interpretation -- run .\examples\interpretation-scripted.json "$job"
npm.cmd run interpretation -- revalidate "$job"
```

Read the retained source and evidence before deciding. For the simple fictional `row-1`, after comparing the association:

```powershell
npm.cmd run interpretation -- review "$job" row-1 approve James "Compared the quoted name and score." --confirm-association
npm.cmd run interpretation -- review "$job" row-2 reject James "The proposed old score is contradicted by a correction."
npm.cmd run interpretation -- export "$job"
```

The default export includes only approved **records**. Without approvals, it produces an explicitly empty record list/header-only CSV and reports zero exported. JSON retains the source snapshot, all passage outcomes, evidence, review history and exclusion counts; **approved-only is not source-text redaction**. Diagnostic exports include pending and rejected records with visible statuses and the raw scripted response, preserving even proposed evidence that failed validation:

```powershell
npm.cmd run interpretation -- export "$job" --diagnostic
```

CSV always includes record IDs, review status, requested columns in their declared order and validation issues; spreadsheet-formula prefixes are escaped. JSON retains per-field evidence and source hashes. Retained system findings such as `association_unverified` are not erased by human approval; the review event records how the human accepted the association.

All source snapshots and review artifacts contain user-supplied content. They stay local under the ignored directory by default. Do not commit customer artifacts or credentials.
